## 一、bcrypt 密码哈希

### 学习内容

1. 密码为什么不能明文存储
2. 哈希 vs 加密的本质区别
3. bcrypt 算法原理（Salt + 工作因子）
4. passlib 库的使用
5. 版本兼容问题排查

### 改进前的状态

数据库中密码是这样存的：
```
MySQL > SELECT * FROM users;

id  | username | password
----+----------+-----------
1   | TH       | 123456          ← 明文，谁都能看到
```

`login` 端点的验证逻辑直接用 `!=` 比对：

```python
if user[2] != req.password:    # 明文比对，极其不安全
    return {"message": "密码错误"}
```

### 存在的问题

| 问题 | 风险 |
|------|------|
| 数据库泄露 | 所有用户密码直接暴露 |
| 开发者可见 | 我自己能直接看到用户密码 |
| 撞库攻击 | 用户在其他网站用相同密码，一并被破 |

### 改进方案

安装 `passlib[bcrypt]`，在 `auth_service.py` 中新增两个函数：

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    """把明文密码变成哈希值"""
    return pwd_context.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """验证密码是否正确"""
    return pwd_context.verify(plain_password, hashed_password)
```

改动点：

| 文件 | 改动 |
|------|------|
| `auth_service.py` | 新增 `hash_password()` 和 `verify_password()` |
| `database.py` | `create_user()` 参数名从 `password` 改为 `password_hash` |
| `main.py` `/register` | 存入前调用 `hash_password(req.password)` |
| `main.py` `/login` | `!=` 改为 `verify_password(req.password, user[2])` |

### 遇到的问题

**问题 1：passlib 与新版 bcrypt 不兼容**

`pip install passlib[bcrypt]` 后运行注册接口，报错：

```
AttributeError: module 'bcrypt' has no attribute '__about__'
```

原因：passlib 已经几年没更新，新版 bcrypt (4.1+) 移除了一些旧接口，passlib 识别不了。

解决：降级 bcrypt 到兼容版本 `pip install bcrypt==4.0.1`。

**教训**：以后看到 `AttributeError: module 'xxx' has no attribute 'yyy'`，第一反应就是依赖版本不兼容。

**问题 2：旧数据怎么办**

数据库里之前测试注册的用户，密码还是明文存的。用 `verify_password()` 验证会失败（明文和哈希值格式完全不同）。

解决：清空三张表数据，重新注册。删除顺序必须先子表后主表（外键约束）：

```sql
DELETE FROM travel_history;
DELETE FROM user_profile;
DELETE FROM users;
```

### 改进后的状态

注册时，密码经过 bcrypt 哈希再存入：

```
用户注册 "123456"
     ↓
hash_password("123456")
     ↓
存入数据库: "$2b$12$LJ3m4ys3GZ8qK7vRxFb1eOjWkP..."
              ↑ 不可逆的哈希值，谁也看不出原密码
```

登录时，用 `verify_password()` 验证：

```
用户输入 "123456"  +  数据库哈希值 "$2b$12$LJ3m4ys3GZ..."
        ↓
verify_password() 用同样的 salt 重新哈希输入的密码
        ↓
比对两个哈希值 → 相同则通过
```

### 收获

1. **哈希是单向的，加密是双向的**——密码应该用哈希，不是加密。即使是开发者也不应该能反推出用户的密码
2. **bcrypt 哈希值长什么样**：`$2b$12$Salt(22位)哈希值(31位)`，包含算法版本、工作因子、Salt、哈希值四个部分
3. **Salt 的作用**：同样的密码 "123456"，每次 bcrypt 产生的哈希值都不同，因为 Salt 是随机的。这防止了彩虹表攻击
4. **工作因子 12**：`$12` 表示 2¹² = 4096 轮哈希计算。越大越安全，但也越慢
5. **deprecated="auto"**：如果未来 bcrypt 被淘汰，passlib 会自动切换到新算法，代码不用改
6. **测试数据不值得心疼**：开发阶段的脏数据，上线前全部清掉，不要因为"舍不删"而保留明文密码

## 二、JWT Bearer Token 标准化

### 学习内容

1. HTTP 认证的标准格式（Bearer Token）
2. FastAPI HTTPBearer 依赖注入
3. Swagger UI Authorize 按钮的原理
4. token 传输的两种方式对比

### 改进前的状态

`dependency.py` 使用手动 Header 解析：

```python
from fastapi import Header

def get_current_user(authorization: str = Header(None)):
    if not authorization:
        return None
    user_id = verify_token(authorization)
    return user_id
```

问题：

| 问题 | 影响 |
|------|------|
| 手动读 Header，不规范 | 与标准做法不一致 |
| Swagger UI 没有 Authorize 按钮 | 每次手动填 token 参数 |
| 参数表格里填了不生效 | Swagger 不认为这是认证字段，不自动带上 |

### 改进方案

改为 FastAPI 标准的 `HTTPBearer` 方式：

```python
from fastapi.security import HTTPBearer

security = HTTPBearer()

def get_current_user(credentials = Depends(security)):
    token = credentials.credentials   # FastAPI 自动把 "Bearer " 前缀去掉
    user_id = verify_token(token)
    return user_id
```

改动后：

- Swagger UI 右上角出现 🔒 Authorize 按钮
- 点按钮输入 token，后续所有请求自动带上 `Authorization: Bearer xxx` header
- `credentials.credentials` 自动把 `"Bearer eyJhbGci..."` 去掉前缀，只返回纯 token

### 遇到的问题

**问题：Swagger Authorize 按钮发了 `Bearer eyJhbGci...`，但 verify_token 不认识**

原因：原来的代码发的是纯 token `eyJhbGci...`（不加 `Bearer ` 前缀），而 HTTPBearer 标准格式是 `Bearer eyJhbGci...`。

解决：`credentials.credentials` 这个属性已经自动去掉了 `Bearer ` 前缀，拿到的就是纯 token。所以 `verify_token()` 不需要任何改动，直接就能用。

### 收获

1. **标准永远比自定义好**：即使习惯了手动写 Header，也应该用框架提供的标准方式。接前端、给别人用、写文档都能省掉很多解释成本
2. **Bearer Token 格式**：`Authorization: Bearer <token>`，Bearer 表示"持有者"，意思是"谁持有这个 token 谁就是合法用户"
3. **Depends 依赖注入**：`credentials = Depends(security)` 是 FastAPI 的依赖注入，它不仅提供认证信息，还让 Swagger 自动识别这是认证端点
4. **Swagger UI 的 Authorize 按钮**：只有使用 FastAPI 标准安全方案（HTTPBearer、OAuth2 等）才会出现。手动 `Header(None)` 不会有

## 三、同步到异步的逐步迁移

### 学习内容

1. 同步和异步的本质区别
2. `async def` 和 `await` 的使用
3. `httpx.AsyncClient` 替代 `requests`
4. FastAPI 混合同步与异步的能力
5. 异步的"传染性"（async 函数调用方必须 await）
6. 异步的适用场景判断

### 核心概念理解

**餐厅服务员的比喻：**

```
同步：
服务员A → 接待客人1 → 去厨房下单 → 站在厨房门口干等 → 端菜 → 接待客人2
                         ↑ 等待期间什么都做不了

异步：
服务员A → 接待客人1 → 去厨房下单 → 立即回来接待客人2 → 去厨房下单 → 立即回来接待客人3
                         ↑ 不等人                         ↑ 不等人
厨房好了叫一声，服务员去端菜
```

**关键认知**：异步不是让菜做得更快，而是让服务员在等菜时不被绑定。FastAPI 服务器就是服务员，每个请求就是一个客人。

### 改进前的状态

所有文件使用 `requests`（同步 HTTP 库），所有函数都是 `def`：

```python
import requests

def extract_travel_info(api_key, message):
    response = requests.post(url, headers=headers, json=data)  # 阻塞，等 1-3 秒
    result = response.json()
    return json.loads(result["choices"][0]["message"]["content"])
```

### 改进方案

只改 HTTP 层（调 DeepSeek 的部分），数据库层不动。因为：

- DeepSeek API 调用：等待 1-3 秒，是真正的瓶颈
- MySQL 数据库查询：等待 50ms，不值得折腾
- FastAPI 允许 async 路由里直接调同步函数，它自动丢线程池

改动范围：

| 文件 | 改动 | 说明 |
|------|------|------|
| `ai_service.py` | `requests` → `httpx`，2 个函数加 `async`/`await` | 信息提取 + 攻略生成 |
| `tool_router.py` | `requests` → `httpx`，1 个函数加 `async`/`await` | 工具选择 |
| `summary_service.py` | `requests` → `httpx`，2 个函数加 `async`/`await` | 画像总结 + 历史总结 |
| `recommend_service.py` | `requests` → `httpx`，1 个函数加 `async`/`await` | 城市推荐 |
| `analysis_service.py` | `requests` → `httpx`，1 个函数加 `async`/`await` | 用户分析 |
| `main.py` `/chat` | `def` → `async def`，调用 async 函数加 `await` | 旅游规划 |
| `main.py` `/agent` | `def` → `async def`，调用 async 函数加 `await` | Agent 路由 |

不改的：

| 文件 | 原因 |
|------|------|
| `database.py` | pymysql 保持同步，查询只要 50ms |
| `agent_service.py` | 只是 database 的壳，database 不变它就不变 |
| `auth_service.py` | JWT 是纯 CPU 计算，没有 IO 操作 |
| `main.py` 其他端点 | `/register` `/login` `/history` `/profile` 只调同步函数 |

### 遇到的问题

**问题 1：遗漏 `await`**

`/agent` 端点的 `summarize_profile()` 调用漏了 `await`：

```python
# 其他 6 个 async 调用都加了 await，就这个没加
answer = summarize_profile(DEEPSEEK_API_KEY, profile)  # 忘了 await
```

报错：

```
TypeError: 'coroutine' object is not iterable
```

原因：`async def` 函数不加 `await` 调用，返回的不是结果，而是一个协程对象。FastAPI 尝试把协程对象序列化成 JSON，崩溃。

**教训**：异步有"传染性"——async 函数的所有调用方都必须加 `await`。漏掉一个，整个链就断了。

**问题 2：只改了 service 层，忘了改路由**

先把 5 个 service 文件全改成了 async，但 `main.py` 里的 `/chat` 端点是 `def`，也没有 `await`。报错：

```python
parsed_data = extract_travel_info(...)  # async函数，没加await
parsed_data.get("profile", {})          # 报错：协程对象没有 .get() 方法
```

**教训**：改 async 要从下往上改，但验证要从上往下测。任何一个环节断了都会爆。

**问题 3：httpx.ConnectError 网络问题**

改用 `httpx` 后偶尔报 `httpx.ConnectError`，连不上 DeepSeek API。原因是 `httpx` 和 `requests` 处理系统代理的方式不同，以及偶发的网络波动。

解决：确认是偶发问题，重启 uvicorn 后恢复正常。

### 收获

1. **异步不加速单次请求**：DeepSeek 生成还是 1-3 秒，不会变快。异步的价值在于并发——100 个用户同时请求时，异步不会阻塞，同步需要排队
2. **个人项目用异步收益低**：我一个人用，永远不会出现并发场景。做异步是为了面试能说清楚原理，不是为了性能
3. **异步有"病毒"特性**：一个函数变成 async，调用方全得加 await，一路传染。所以改异步要权衡成本
4. **别为了用而用**：技术选择要匹配场景。全项目异步化工作量很大（要换 aiomysql、所有 database 函数改 async），但对我现在的使用场景收益为零。只改 HTTP 层（httpx），不改数据库，是性价比最高的方案
5. **`async with` 管理连接生命周期**：`AsyncClient` 需要正确打开和关闭，`async with` 确保用完自动释放资源

```

✓ Swagger UI 可视化接口文档 + Authorize 一键认证
✓ AI 旅游攻略生成（异步 httpx 调用 DeepSeek）
✓ 用户画像持久化（MySQL 存储）
✓ 旅行历史记录
✓ Agent 工具路由（history / profile / travel / recommend / analysis）
✓ 个性化城市推荐 + 用户行为分析
✓ async/await 异步架构（HTTP 层）
```

## 关键认知变化

今天最大的收获不是代码，是三个认知：

1. **安全是底线，不是功能**——bcrypt 不是"加分项"，是"必须项"。面试官看到明文密码直接淘汰
2. **标准比习惯重要**——JWT Bearer 格式、HTTPBearer 依赖注入，用标准做法让 Swagger 自动识别、前端直接对接，省掉无数沟通成本
3. **技术选型要问"为什么"**——异步很好，但我一个人用的本地项目全异步化收益接近零。理解原理、能在面试讲清楚、部分实践，就够了
