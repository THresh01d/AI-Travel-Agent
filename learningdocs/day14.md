## 一、RAG 是什么

### 学习内容

1. Embedding 向量化原理
2. 语义搜索 vs 精确匹配
3. ChromaDB 向量数据库的使用
4. RAG 的完整流程：检索 → 增强 → 生成
5. 向量检索结果的评估

### RAG 解决的核心问题

**改进前的痛点：**

项目一开始有个 `knowledge_base.py`，是一个城市→景点列表的字典：

city_spots = {
    "北京": ["故宫", "天安门", "颐和园"],
    "成都": ["宽窄巷子", "熊猫基地", "春熙路"],
    ...
}

问题：

| 问题 | 场景 |
|------|------|
| 精确匹配死板 | 用户说"想看大熊猫"→ 不知道匹配哪个城市 |
| 信息太少 | 只有景点名字，AI 生成攻略时没有详细参考 |
| 无法扩展 | 加新城市要手写代码 |

**改进后：**

用 ChromaDB 向量数据库存储 17 条景点详细描述。用户说"我想去看大熊猫"，不依赖城市名，直接语义搜索匹配到"成都大熊猫繁育研究基地"。

用户说"我想去看大熊猫"
     ↓
Embedding 向量化 → [0.12, -0.34, 0.87, ...]
     ↓
ChromaDB 向量相似度搜索
     ↓
匹配到："成都大熊猫繁育研究基地位于成都北郊，是全球最大的..."
     ↓
注入 Prompt + 补全城市名 → AI 生成攻略


### 技术实现

**技术栈：**
- ChromaDB：轻量级本地向量数据库
- `DefaultEmbeddingFunction()`：ChromaDB 自带的 embedding 模型（384 维）
- 数据存放路径：`./chroma_data/`

**项目结构变化：**

新增：
app/
└── knowledge/
    ├── __init__.py
    ├── spots_data.py      ← 17 条景点描述数据
    └── vector_store.py    ← ChromaDB 初始化 + 检索函数

删除：
app/knowledge_base.py       ← 旧的 city_spots 字典，被 RAG 替代

**检索函数设计：**

def search_spots(query: str, top_k: int = 3) -> tuple[str, str]:
    """返回 (拼接的景点描述文本, 推断的城市名)"""

返回两个值：描述文本用于注入 Prompt，城市名用于补全 AI 没识别出来的 destination。

### 遇到的问题

**问题 1：sentence-transformers 导入太慢**

一开始用 `sentence-transformers` 库加载本地模型，底层依赖 `transformers`，导入时卡死。

解决：换用 ChromaDB 自带的 `DefaultEmbeddingFunction()`，基于 ONNX，轻量很多，不需要额外装模型。

**问题 2：数据变长了，反而不方便？**

原来的 `city_spots` 字典一个景点就 3 个字，现在每条数据有 city、name、type、description 四个字段。

这恰恰是 RAG 需要的——文字越长，语义信息越丰富，检索越准确。17 条数据是主动设计的知识条目，不是负担。

**问题 3：RAG 匹配到了好景点，但 AI 不推荐**

用户说"想看大熊猫"，RAG 匹配到成都熊猫基地。但用户的 profile 里有"晚起、小众景点"，AI 判断熊猫基地人多要早起，不推荐。

**根因**：Prompt 没有告诉 AI"用户明确说了的需求，优先级高于个人偏好"。

**当前态度**：这是 Prompt 优化问题，后面再处理。先让流程跑通。

### 收获

1. **Embedding 的本质**：把文字变成数字向量。语义相近的文字，向量距离也相近。"大熊猫"和"成都熊猫基地"向量相似度 0.79，"火锅"只有 0.49
2. **RAG 不是魔法**：检索到的东西 ≠ AI 一定会用。Prompt 设计决定了 AI 怎么对待检索结果
3. **数据质量 > 数据数量**：17 条有质量的描述，比 1000 条垃圾数据更有用
4. **ChromaDB 的适用场景**：轻量级、本地运行、不需要分布式。适合个人项目和原型

## 二、项目结构统一：/chat 合并到 /agent

### 学习内容

1. 功能去重：识别重复逻辑
2. API 设计：单一入口 vs 多入口
3. 数据流顺序：提取 → 修正 → 存储

### 改进前的状态

项目有两个对话入口：

| 端点 | 功能 | 问题 |
|------|------|------|
| `/chat` | 提取信息 → 存画像 → 生成攻略 | 固定流程，用户说"分析习惯"也生成攻略 |
| `/agent` | AI 判断意图 → 选工具 | 能处理多种意图，但 travel 工具没有 profile 保存 |

两个入口有很多重复逻辑（AI 提取、RAG 搜索、攻略生成），维护时容易漏。

### 改进方案

删除 `/chat`，把它的功能合并到 `/agent/travel` 分支中。所有用户对话统一走 `/agent`。

**合并清单：**

| 从 `/chat` 搬过来的 | 搬到 `/agent` 哪里 |
|-------------------|------------------|
| profile 保存（`save_profile`） | `travel` 分支 + `profile` 分支 |
| RAG 搜索 | `travel` 分支 |

### 数据流优化

**修正前的顺序：**
```
AI 提取 → 直接存 history → RAG 搜索 → 生成攻略
              ↑ 脏数据已经入库
```

**修正后的顺序：**
```
AI 提取 → 存 profile → load profile → RAG 搜索 → 补全 city + 兜底 days → 存 history → 生成攻略
                                                            ↑ 数据干净了再存
```

### history 存储策略优化

**改进前：** 只要 `city` 不为空就存。用户说"想去看大熊猫"→ `rag_city` 补全为"成都"→ 存入 history。

问题：用户只是表达兴趣，没有明确出行计划。

**改进后：** 只有同时满足两个条件才存：

```python
ai_city = parsed_data.get("destination")   # AI 从用户原话提取的城市

if ai_city and parsed_data.get("days"):    # 用户明确说了城市 + 天数
    save_history(...)
```

| 用户说 | ai_city | days | 存 history？ |
|--------|---------|------|-------------|
| "成都三日游预算1500" | "成都" | 3 | ✅ 明确规划 |
| "我想去看大熊猫" | None | None | ❌ 兴趣表达 |
| "推荐我去哪玩" | None | None | ❌ 探索意图 |

这样 history 表只记录真正有出行意图的规划。

### 最终架构

```
用户一句话
     ↓
POST /agent
     ↓
choose_tool() → AI 判断意图
     ↓
┌────────┬────────┬────────┬────────┬────────┐
│ history│profile │recommend│analysis│ travel │
│ 查历史 │提取+存 │推荐城市 │分析习惯 │提取信息│
│ +总结  │画像+总 │        │        │存画像  │
│        │结      │        │        │RAG搜索 │
│        │        │        │        │补全城市│
│        │        │        │        │存历史  │
│        │        │        │        │生成攻略│
└────────┴────────┴────────┴────────┴────────┘
```

### 收获

1. **功能去重**：两个端点做类似的事 → 合并。代码少了，维护成本低了
2. **数据流顺序很重要**：先修正数据，再存储。顺序错了 = 脏数据入库
3. **存什么要想清楚**：不是所有用户输入都值得持久化。模糊意图不该进 history
4. **RAG 补全 ≠ 用户意图**：`rag_city` 是用来检索的辅助信息，不代表用户真的想去那里
